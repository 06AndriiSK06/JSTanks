# JSTanks Arena (`v1.0.0`)

Багатокористувацька браузерна арена в реальному часі з авторитативним 30 Гц сервером на Node.js, детермінованою фізикою спільного ядра (`@jstanks/shared`), бінарним мережевим протоколом, прогнозуванням на клієнті, інтерполяцією сутностей, записом і відтворенням матчів у NDJSON та продакшн-контейнеризацією з обсервабільністю.

## 1. Швидкий старт

### Запуск у Docker (рекомендовано для продакшн)

```bash
cp .env.example .env
docker compose up --build -d
```

Гра, REST API та метрики будуть доступні за адресою: `http://localhost:3000`.

### Локальний запуск для розробки

```bash
npm ci
npm run build
npm --workspace=@jstanks/server run dev
```

У другому терміналі (за потреби hot-reload клієнта):

```bash
npm --workspace=@jstanks/client run dev
```

### Перевірка якості, типів та тестів

```bash
npm run typecheck
npm run lint
npm test
npm run test:e2e
```

## 2. Архітектура системи

```text
+-------------------------------------------------------------------+
|                        Browser Client (PWA)                       |
|  Canvas 2D Renderer + Web Audio + Virtual Joystick + SW Cache     |
|  Client-Side Prediction (CSP) & Reconciliation + Interpolation    |
+---------------------------------+---------------------------------+
                                  |
                   HTTPS / WSS (JSON & Binary Codec)
                                  |
                                  v
+-------------------------------------------------------------------+
|                  Authoritative Node.js Server                     |
|  HTTP Server: /, /health, /ready, /metrics, /api/rooms, /replays  |
|  WS Gateway: Origin check, per-IP limit, token-bucket rate limit  |
|  RoomManager -> Room (30 Hz fixed-step loop) -> BotPlayer AI      |
|  Observability: pino JSON logs + prom-client + NDJSON MatchLog    |
+---------------------------------+---------------------------------+
                                  |
                                  v
+-------------------------------------------------------------------+
|                   Shared Core (@jstanks/shared)                   |
|  Pure Deterministic Simulation (fixed dt = 1/30 s, Mulberry32)    |
|  Zod Schemas + Binary Encoder/Decoder (little-endian ArrayBuffer) |
+-------------------------------------------------------------------+
```

### Структура монорепозиторію

- `shared/` (`@jstanks/shared`) — чиста детермінована симуляція (`SharedWorld`), фізика зіткнень, генератор псевдовипадкових чисел `Mulberry32`, Zod-схеми повідомлень і компактний бінарний кодек.
- `server/` (`@jstanks/server`) — авторитативний сервер на чистому `node:http` + `ws`, керування кімнатами (`RoomManager`), серверні боти (`BotPlayer`), запис і стримінг повторів у NDJSON, логування `pino`, метрики Prometheus (`/metrics`) та Graceful Shutdown по `SIGTERM`.
- `client/` (`@jstanks/client`) — клієнт на Vite + TypeScript + HTML5 Canvas, прогнозування власного руху та звірка (`reconciliation`), інтерполяція віддалених об'єктів з буфером затримки, діагностичний оверлей (`F3`), Web Audio, мобільний віртуальний джойстик і PWA (`manifest.webmanifest` + `sw.js`).
- `e2e/` — наскрізні тести Playwright для перевірки одночасної гри двох клієнтів у реальному часі.

## 4. Мережевий протокол та вимірювання

### Формат протоколу

- **Керування та події (JSON):** `join`, `welcome`, `roster`, `chat`, `ping`, `pong`, `gameEvent`, `shutdown`.
- **Високочастотний потік 30 Гц (Binary):** компактні little-endian пакети `ArrayBuffer` для команд вводу (`input`) і знімків стану світу (`snapshot`) без накладних витрат парсингу JSON.

### Зведена таблиця вимірювань (Лаб 5, Лаб 7 та Лаб 8)

| Показник                                                        | Виміряне значення                                                  | Цільовий бюджет / вимога           |
| :-------------------------------------------------------------- | :----------------------------------------------------------------- | :--------------------------------- |
| Розмір кадру знімка світу (JSON vs Binary, 16 сутностей)        | ~1 480 Б (JSON) vs ~364 Б (Binary) — **економія ~75%**             | Суттєве зменшення трафіку на 30 Гц |
| Середній крок симуляції на 1 кімнату (32 гравці + боти)         | `~1.8 мс` (p99 `~4.2 мс`)                                          | `< 33.3 мс` (бюджет тіку 30 Гц)    |
| Максимальне навантаження одного процесу (4 кімнати × 32)        | 128 учасників, ELU `< 0.45`, RSS `~115 МБ`                         | Стабільний 30 Гц без деградації    |

## 5. Експлуатаційні межі одного процесу та моніторинг

- **Межі одного процесу:** один інстанс Node.js комфортно обслуговує до **20 активних кімнат** або сумарно до **128–160 активних учасників** на частоті 30 Гц у межах одного потоку V8 без зростання затримок Event Loop (`ELU < 0.5`).
- **Обсервабільність:**
  - `GET /health` — швидка перевірка живості процесу (`status`, `version`, `uptimeSec`, `rooms`, `rssBytes`).
  - `GET /ready` — готовність приймати новий трафік (`200 OK` під час роботи, `503 Service Unavailable` під час зупинки).
  - `GET /metrics` — метрики у форматі Prometheus (`jstanks_connected_players`, `jstanks_active_rooms`, `jstanks_ws_messages_total`, `jstanks_ws_bytes_total`, `jstanks_tick_duration_ms`, `jstanks_event_loop_utilization`, `jstanks_process_rss_bytes`, `jstanks_ws_rejections_total`).
- **Подальше горизонтальне масштабування:** завдяки розділенню на незалежні кімнати з власним станом у пам'яті, наступним кроком масштабування є винесення маршрутизації кімнат у Redis та балансування WebSocket-з'єднань за `roomId` (sticky routing) перед кількома репліками контейнера.

## 6. Нотатки до захисту (Reflection)

1. **Еволюція архітектури від прототипу (Лаб 1) до релізу (Лаб 8):** у перших роботах логіка гри, фізики та відмальовування була монолітно пов'язана у клієнтському браузері. Поступово симуляцію було відокремлено у чистий детермінований пакет `@jstanks/shared`, переведено на авторитативний сервер Node.js з фіксованим кроком 30 Гц, оптимізовано мережевий шар бінарним протоколом і клієнтським прогнозуванням, покрито тестами (unit, property-based, load, E2E, chaos) та запаковано у безпечний Alpine Docker-контейнер із метриками та CI/CD.
2. **Найскладніша проблема та її розв'язання:** найскладнішим виявилося забезпечення плавного руху на клієнті за наявності мережевої затримки (`RTT`) та втрат пакетів без розсинхронізації зі станом сервера. Проблему вирішено комбінацією буферизації команд із порядковими номерами (`seq`), миттєвого локального прогнозування на клієнті, м'якої звірки (`reconciliation`) при отриманні підтвердженого знімка від сервера та буферизованої інтерполяції для інших гравців.
3. **Що можна покращити в наступній версії (`v2.0`):** додати горизонтальне масштабування через Redis Pub/Sub і маршрутизацію за кімнатами для розподілу навантаження між кількома нодами, а також систему авторизації та таблицю рекордів у зовнішній БД.
