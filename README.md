# JSTanks — Lab 02: Objects, Prototypes, and `this`: The Entity Model

Аркадна 2D-гра про керування танком на полігоні (ES Modules, Vite, Canvas 2D API) із фіксованим кроком симуляції (`60 Hz`), об'єктно-орієнтованою моделлю сутностей, сховищем світу на базі `Map`, системою колізій коло–коло та композиційними компонентами.

## Запуск проєкту

```bash
npm install
npm run dev
```

Перевірка форматування та лінтера (Biome):

```bash
npm run format
npm run lint
```

### Керування

- `W` / `S` або `↑` / `↓` — рух уперед / задній хід
- `A` / `D` або `←` / `→` — поворот корпусу танка
- `Space` або `F` — постріл зі ствола бронебійним снарядом
- `E` або `Left Shift` — запуск самонавідної ракети (`homing`)

## Архітектура моделі сутностей (Milestones M1–M3)

- `src/sim/vector.js` — клас `Vector2` із чистими (імутабельними) методами (`add`, `sub`, `scale`, `length`, `normalize`, `rotate`, `dot`, `distanceTo`, `static fromAngle`).
- `src/sim/entity.js` — базовий клас `Entity` із приватним статичним лічильником `static #nextId = 1` та приватним полем `#id` (`get id()`), позицією, швидкістю, радіусом та методом `update(dt, world)`.
- `src/sim/ship.js` — `class Ship extends Entity` (рівно **один рівень спадкування**). Інкапсулює приватне здоров'я `#hp` та публічний геттер `get hp()`, перезарядку гармати, стрільбу зі ствола `fire()` та автоматичний респаун через `2.0 с` у безпечній точці арени.
- `src/sim/world.js` — клас `World` поверх `Map<number, Entity>`. Підтримує `spawn`, відкладене видалення `despawn` + `sweep` наприкінці кроку (щоб не мутувати колекцію під час ітерації), ітератор `[Symbol.iterator]()` та генератор `*ofKind(kind)`.
- `src/sim/bullet.js`, `src/sim/asteroid.js`, `src/sim/pickup.js`, `src/sim/explosion.js` — сутності снарядів (з `TTL`), астероїдів-перешкод, стаціонарних бонусів (`shield`, `rapid`) та частинок вибуху.
- `src/sim/collision.js` — ізольована система колізій коло–коло (`O(n²)`), яка повертає пари перетнутих сутностей `[a, b]` і легко замінюється на Spatial Hash у наступних лабораторних.

## Баг із втратою контексту `this` та його виправлення

### У чому суть проблеми

У JavaScript значення `this` визначається не місцем оголошення методу в класі, а **точкою виклику** (call site) за чотирма правилами пріоритету:

1. **`new` binding** (`new Ship()`) — `this` вказує на новостворений об'єкт.
2. **Explicit binding** (`fn.call(obj)`, `fn.apply(obj)`, `fn.bind(obj)`) — `this` задається явно.
3. **Implicit binding** (`ship.fire()`) — `this` вказує на об'єкт зліва від крапки.
4. **Default binding** (`const fn = ship.fire; fn()`) — у strict mode (а всі ES-модулі та тіла класів завжди працюють у strict mode) `this === undefined`.

Якщо наївно передати метод у слухач подій:

```js
window.addEventListener("keydown", ship.fire);
```

ми передаємо посилання на функцію без об'єкта зліва від крапки. Під час натискання клавіші браузер викликає колбек як звичайну функцію (або з `this = window`), і всередині `fire()` звернення до `this.isSpawned()` падає з помилкою `TypeError: Cannot read properties of undefined`.

### Обране рішення та альтернативи

У нашому проєкті використано **опитування стану клавіатури всередині `ship.update(dt, world)`**, де метод викликається через implicit binding (`entity.update(dt, this)`), тому `this` гарантовано вказує на поточний екземпляр `Ship`.

Три класичні способи фіксу для прямих колбеків та їхні компроміси:

1. **Стрілкова обгортка:** `() => ship.fire()` — лексично захоплює `ship` із замикання; зручно, але створює нову функцію на кожну підписку.
2. **Явне зв'язування:** `ship.fire.bind(ship)` — повертає нову функцію з назавжди зафіксованим `this`; зручно коли потрібно передати посилання на функцію для подальшого `removeEventListener`.
3. **Стрілкове поле класу:** `fire = () => { ... }` — `this` прив'язується до екземпляра при створенні; читається чисто, але створює окрему копію функції в пам'яті для кожного об'єкта замість спільного методу на `Ship.prototype`.

## Дизайн-рішення: композиція замість глибокої ієрархії класів (Milestone M4)

### Як виглядала б глибока ієрархія спадкування і чому вона ламається

Якби ми будували гру через класичне багаторівневе спадкування (`extends`), дерево класів швидко перетворилося б на жорстку конструкцію:

```text
Entity
 ├── MovingEntity
 │    ├── Ship
 │    │    └── PlayerShip
 │    ├── Bullet
 │    │    └── HomingBullet      <-- самонаведення №1
 │    └── Asteroid
 │         └── HomingAsteroid    <-- дублювання логіки самонаведення №2
 └── StationaryEntity
      └── Pickup
           └── ShieldPickup / RapidPickup
```

Така ієрархія має три критичні проблеми:

1. **Дублювання коду (проблема ромба):** логіка самонаведення (`homing`) потрібна одночасно і ракетам (`Bullet`), і ворожим дронам-астероїдам (`Asteroid`). У дереві одинарного спадкування JS ми змушені або дублювати код повороту до цілі в двох гілках, або виносити його в базовий `MovingEntity`, де він не потрібен звичайним кулям.
2. **Комбінаторний вибух класів:** якщо додати ще одну властивість (наприклад, розривний снаряд або бонус, що рухається), кількість комбінацій класів (`ExplosiveHomingBullet`, `MovingPickup`) зростає експоненційно.
3. **Крихкість змін:** будь-яка зміна поведінки в проміжному класі (`MovingEntity`) ризикує зламати всіх його нащадків.

### Чому обрано композицію

Замість питання _«чим є об'єкт у дереві класів?»_ ми використовуємо підхід _«які незалежні поведінки (компоненти) має об'єкт?»_:

- **Компонент самонаведення (`src/sim/components.js`):** функція `createHoming(...)` створює легкий об'єкт стану (`targetKind`, `turnRate`, `range`, `maxSpeed`), а `updateHoming(entity, world, dt)` керує доворотом будь-якої сутності, у якої є поле `entity.homing`. Завдяки цьому один і той самий модуль без жодного дублювання працює і на самонавідних ракетах гравця (`Bullet`), і на астероїдах-переслідувачах (`Asteroid`).
- **Сутності як набори даних та поведінки (`Pickup`):** бонус (`Pickup extends Entity`) не наслідує `Ship` і не потребує проміжного `StationaryEntity` — він просто має нульову швидкість, радіус колізії та поле `pickupType`, а система колізій `World` обробляє пару `[ship, pickup]`.
- Спадкування обмежене строго **одним рівнем** (`Entity` → конкретна сутність), що робить код гнучким, простим для тестування та готовим до мережевої серіалізації у наступних лабораторних роботах.
