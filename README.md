JSTanks — Lab 01: The Event Loop Is the Game Loop
Браузерна 2D-гра про керування танком на полігоні, побудована на чистому JavaScript (ES Modules), Vite та Canvas 2D API із фіксованим кроком симуляції (60 Hz) та інтерпольованим рендерингом (requestAnimationFrame).
Запуск проєкту
npm install
npm run dev

Перевірка форматування та лінтера (Biome):
npm run format
npm run lint

Керування
• W / S або ↑ / ↓ — рух уперед / задній хід
• A / D або ← / → — поворот корпусу танка
• Space — короткочасний форсаж гусениць (перевірка edge-triggered вводу justPressed)
Архітектура проєкту
• src/loop.js — ігровий цикл на requestAnimationFrame з акумулятором (step = 1/60), обмеженням дельти кадру (Math.min(rawDt, 0.25)) проти «спіралі смерті», передачею коефіцієнта інтерполяції alpha у рендер та підрахунком метрик (steps/s, frames/s, frame time).
• src/input.js — замикання createInput(target), яке інкапсує стан клавіш (isDown та одноразове justPressed з очищенням наприкінці кроку симуляції).
• src/sim/ship.js, src/sim/arena.js — чиста математична симуляція фізики танка та «загортання» меж арени (wrap-around) без жодних залежностей від DOM чи Canvas.
• src/render/canvas.js, src/render/draw.js — ініціалізація Canvas з урахуванням devicePixelRatio, лінійна та кутова (lerpAngle) інтерполяція між попереднім і поточним станом танка, рендер полігону та HUD.
Налаштування фізики танка (Milestone M2)
Під час тестування підібрано параметри, щоб танк відчувався важким, але керованим:
• turnSpeed: 3.1 rad/s — плавний розворот корпусу без надмірної різкості.
• forwardAccel: 540 px/s² та reverseAccel: 320 px/s² — передній хід помітно динамічніший за задній.
• drag: 2.4 — експоненційне затухання швидкості (Math.exp(-drag \* dt)), що не залежить від частоти кадрів.
• maxSpeed: 340 px/s — обмеження швидкості, щоб танк не розганявся до неконтрольованих значень.
Експерименти: «Зламай навмисно і поміряй» (Milestone M4)
Базові показники на дисплеї 144 Гц у нормальному режимі:
• steps/s: 60 Hz
• frames/s: 144 fps
• frame time: 0.20–0.40 ms
Експеримент 1. Синхронне блокування потоку на 100 мс кожен 60-й кадр
У функцію render кожен 60-й кадр додано цикл while (performance.now() < t + 100) {}.
• Виміряні показники: frames/s впав зі 144 fps до 118 fps, frame time на заблокованому кадрі підстрибував до ~100.3 ms, тоді як steps/s залишався на рівні 60 Hz.
• Що бачить гравець: кожні ~0.42 с картинка завмирає на 100 мс (відчутний мікрофриз), після чого танк ривком перестрибує вперед.
• Пояснення через Event Loop: JavaScript виконується в одному головному потоці (main thread). Поки функція в Call Stack не завершиться (run-to-completion), Event Loop не може перейти до етапів рендерингу браузера (style -> layout -> paint) і не може обробити нові події клавіатури з черги задач. Жоден асинхронний колбек у тому ж потоці не здатний перервати синхронний цикл while. Після завершення блокування акумулятор бачить накопичений час (~100 ms) і за один кадр виконує ~6 кроків фізики по 16.67 ms підряд, тому steps/s зберігається.
Експеримент 2. Заміна requestAnimationFrame на setInterval(frame, 16)
Цикл переведено на макрозадачу setInterval(..., 16) із заміром інтервалів dt протягом 10 секунд та перемиканням у фонову вкладку на 5 секунд.
• Виміряні показники: frames/s: 63 fps (замість 144 fps на 144 Гц дисплеї); minDtMs: 2.10 ms; maxDtMs: 1006.50 ms (під час переходу у фонову вкладку).
• Що змінилося: 1) Частота рендеру обмежилася ~62.5–63 кадрами/с (1000 / 16), втративши плавність 144 Гц монітора. 2) Виник джиттер (нерівномірність інтервалів між кадрами, аж до 2.1 ms), оскільки setInterval планує макрозадачі в Task Queue без прив'язки до вертикальної синхронізації (VSync) монітора. 3) При перемиканні на іншу вкладку браузер не зупинив цикл повністю (як це робить rAF), а продовжив виконувати тики в фоні з тротлінгом ~1 раз на секунду (maxDtMs = 1006.5 ms).
Експеримент 3. Змінний крок simulate(dt) проти фіксованого кроку 1/60
Замірено координату танка після рівно 5 секунд утримання руху вперед (KeyW) зі стартової точки (200, 300):
Режим симуляції Частота кроків Позиція через 5 с (x, y) Відхилення
Фіксований крок (1/60, з акумулятором) 60 Hz (200.00, 674.00) Еталон (детерміновано)
Змінний крок (simulate(dt) без акумулятора) 144 Hz (200.00, 665.63) -8.37 px по осі Y

• Пояснення: при змінному кроці величина dt на кожному кадрі різна (залежить від герцовки монітора та навантаження на CPU). Оскільки інтегрування швидкості, прискорення та опору (damping) виконується дискретними кроками, зміна розміру dt змінює сумарний пройдений шлях за той самий час. Фіксований крок step = 1/60 гарантує повний детермінізм: незалежно від FPS клієнта або навантаження процесора, симуляція виконує однакову кількість однакових кроків і приводить танк у ту саму точку. Це критично для мережевої синхронізації в мультиплеєрі.
